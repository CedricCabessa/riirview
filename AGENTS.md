# AGENTS.md

## Project Overview

riirview is a Rust TUI application (ratatui) for reading GitHub notifications with a custom scoring system. It uses SQLite (Diesel ORM), async HTTP (reqwest/tokio), and a message-passing architecture for the terminal UI.

- **Language:** Rust, edition 2024
- **License:** Apache 2.0

## Build & Run Commands

```bash
# Build
cargo build

# Build (CI mode — warnings are errors)
RUSTFLAGS="-Dwarnings" cargo build

# Run
cargo run

# Check without building
cargo check
```

## Test Commands

```bash
# Run all tests
cargo test

# Run all tests (verbose, as CI does)
cargo test --verbose

# Run a single test by name (substring match)
cargo test test_scorer_score

# Run tests in a specific module
cargo test --lib score::tests

# Run only integration tests
cargo test --test integration_test

# Run a specific integration test function
cargo test --test integration_test test_notifications
```

Tests require `libsqlite3-dev` (Ubuntu) or equivalent SQLite development libraries.

## Lint & Format Commands

```bash
# Format code
cargo fmt

# Check formatting (CI check — fails on diff)
cargo fmt --check

# Run clippy lints
cargo clippy

# Run clippy with CI strictness (warnings = errors)
RUSTFLAGS="-Dwarnings" cargo clippy
```

Pre-commit hooks enforce `fmt`, `cargo-check`, and `clippy` via `doublify/pre-commit-rust`.

## CI Pipeline

The GitHub Actions CI (`.github/workflows/ci.yml`) runs on pushes/PRs to `main`:
1. `cargo fmt --check`
2. `cargo build --verbose`
3. `cargo test --verbose`
4. `cargo clippy`

**CI sets `RUSTFLAGS="-Dwarnings"`** — all warnings are treated as errors. Fix every warning before submitting.

## Project Structure

```
src/
  main.rs       — Entry point: CLI args, tokio runtime, logging, DB init
  lib.rs        — Module declarations, DB connection pool, migrations
  config.rs     — Global Config singleton (OnceLock<Mutex<Config>>)
  dirs.rs       — XDG directory management (data, config, cache)
  gh.rs         — GitHub API client: notifications, PRs, releases, issues
  models.rs     — Diesel ORM models and enums (Notification, NotificationType, NotificationState)
  schema.rs     — Auto-generated by Diesel CLI — do NOT edit manually
  score.rs      — Scoring engine: reads rules from TOML, applies to notifications
  service.rs    — Business logic: sync, query, mark done/read, score updates
  filter.rs     — Search/filter query parser
  tui.rs        — TUI rendering, input handling, message-passing (mpsc channels)
build.rs        — Extracts keymap table from README.md, generates VERGEN git info
migrations/     — Diesel SQL migrations
tests/          — Integration tests with mock HTTP (mockito) and JSON fixtures
```

## Code Style Guidelines

### Formatting

- Enforced by `cargo fmt` with `.rustfmt.toml` (`edition = "2024"`).
- Always run `cargo fmt` before committing.

### Naming Conventions

- **snake_case** for functions, variables, modules (standard Rust).
- **PascalCase** for types, enums, structs.
- **SCREAMING_SNAKE_CASE** for constants (e.g., `NB_TASK`, `MIGRATIONS`, `KEYMAP`).
- Test functions are prefixed with `test_` (e.g., `test_scorer_builder`).
- Test modules are named `mod tests` (prefer plural).

### Imports

- Use `use crate::` for internal module imports.
- Group related imports with nested braces: `use diesel::{prelude::*, ...};`
- In test modules, use `use super::*;`.
- General ordering: std library, external crates, then `crate::` imports.
- Avoid `use crate::*;` — prefer explicit imports (existing usage in `service.rs` is not ideal).

### Error Handling

- Use `anyhow::Result<T>` as the default return type for fallible functions.
- Define custom error enums (with `std::error::Error` + `From` impls) for domain-specific modules (see `gh::Error`, `score::Error`).
- Propagate errors with `?` operator.
- Avoid `.unwrap()` and `.expect()` in non-test code — use `?` or proper error handling instead.
- `.unwrap()` / `.expect()` are acceptable in tests and one-time initialization (e.g., connection pool setup).

### Types

- Use type aliases for complex types: `type DbConnection = PooledConnection<DbConnectionManager>;`
- Derive macros are used extensively: `Debug`, `Clone`, `Deserialize`, `Queryable`, `Selectable`, `Insertable`, etc.
- Enums with Diesel: implement `ToSql`/`FromSql` traits manually for string-backed DB enums.

### Async

- Tokio multi-threaded runtime (`#[tokio::main]`).
- Use `futures::stream` with `buffer_unordered` for concurrent API calls (capped at 30).
- Async tests use `#[tokio::test]`.

### Testing Patterns

- Unit tests live in `#[cfg(test)] mod tests` blocks inside source files.
- Integration tests are in `tests/` with JSON fixtures (`notifications.json`, `pulls.json`, etc.).
- Use `mockito` for HTTP mocking, `tempfile` for temporary files/DBs.
- Use `Config::init_for_test()` to override global config in tests.
- Test assertions use standard `assert!`, `assert_eq!`.

### Database

- `schema.rs` is auto-generated by Diesel CLI — never edit it by hand.
- Run `diesel migration run` to apply migrations.
- Migrations live in `migrations/` as SQL files.

### Comments

- Minimal comments — code should be self-explanatory.
- Use `// TODO:` and `// FIXME:` for known issues.
- No doc comments (`///`) are currently used in this codebase.

### Things to Avoid

- Do not commit `.env` files (contains `GH_TOKEN` and other secrets).
- Do not edit `schema.rs` manually.
- Do not introduce new `.unwrap()` calls outside of tests or initialization.
- Do not ignore clippy warnings — CI treats them as errors.
